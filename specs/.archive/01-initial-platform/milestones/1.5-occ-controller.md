# Feature Spec: Milestone 1.5 — OCC Controller

## Problem and Decision

Namespace creation and deletion already commit durable reconciliation work, but
no independent worker executes it. Milestone 1.5 adds one polling PostgreSQL
worker that safely provisions and deletes Namespaces through the existing
`ComputeDriver`. OCC remains the sole owner of authorization, lifecycle state,
readiness, audit evidence, and the singleton Installation.

Build on the implemented [PostgreSQL persistence](1.3-postgresql-persistence.md)
and [bootstrap, Namespace, and IAM](1.4-bootstrap-namespaces-iam.md) milestones.
The [platform design](../../../../docs/design.md)
remains authoritative. Agent deployment, revision preparation, retirement,
activation, and routing belong to Milestone 1.6.

## Scope

### Changes

- Run a dedicated controller worker separately from the HTTP API.
- Poll existing Namespace lifecycle work, recover abandoned claims, renew leases,
  and dispatch the already selected `ComputeDriver`.
- Reauthorize each persisted initiating actor against current IAM policy before
  an infrastructure effect.
- Publish Namespace status, lifecycle audit, and queue completion or failure in
  one claim-fenced transaction.
- Remove infrastructure work from metadata-only Agent creation; safely consume
  previously recorded Agent metadata work without invoking a Driver.
- Report worker health, supported pending work, and redacted failures through
  the existing process and queue surfaces.

### Does not change

- Singleton Installation ownership, `namespaceId` isolation, exactly one gateway
  per Namespace, existing Driver selection, or OCC-owned readiness.
- Existing queue schema, semantic keys, target states, owner constraints, claim
  exclusion, leases, retry limits, stale recovery, or polling-only discovery.
- Agent deployment, revision admission, revision dispatch or retirement, active
  workloads, routing, production Kubernetes Drivers, or production admission.
- Existing IAM permission vocabulary, bootstrap grants, resource generations,
  worker identities, notification listeners, dependency manifests, additional
  health servers, or archived `legacy/` code.

## Contract

### Work ownership and admission

Namespace creation authorizes the existing `create` permission, inserts
`provisioning`, records `namespace:<namespaceId>:reconcile:ready`, and appends
its success audit before the surrounding transaction commits. Authorized
deletion locks an empty Namespace, changes it to `deleting`, records
`namespace:<namespaceId>:reconcile:deleted`, and appends its audit in the same
transaction. Both targets already exist in the
[operation repository](../../../../packages/occ/src/state/postgres-state.ts).

Readiness is the result of provisioning, not another work item. Agent creation
and metadata updates have no infrastructure effect and create no new work. The
worker may terminalize preexisting generic Agent metadata items as audited
no-ops. Existing `agent_revision:<revisionId>:reconcile` items remain durable
and unclaimed until Milestone 1.6; unsupported rows cannot starve Namespace
claims or appear as actionable Milestone 1.5 backlog.

Supported work is exactly `revision_id IS NULL`: this includes Namespace
lifecycle rows and legacy metadata-only Agent no-ops, and excludes every Agent
revision. Apply that same predicate when claiming, in both stale-claim and
exhausted-queued recovery sweeps, and in worker pending/health counts. Deferred
revision rows must remain completely untouched even if claimed, expired, or
already at their retry limit.

Every work item belongs to exactly one Namespace. The current partial unique
index serializes Namespace lifecycle work per Namespace and Agent/revision work
per Agent while permitting different Agents in one Namespace to proceed
independently. Namespace deletion remains limited to empty Namespaces.

### Authorization and dispatch

One process loads the persisted singleton Installation and existing selected IAM
and Compute Drivers before claiming work; an uninitialized platform, mismatched
Installation, missing Driver, or invalid policy fails closed. Its polling loop
uses the existing queue directly; queue state and structured process events
provide health, supported pending-work counts, and redacted failures without a
second service, health listener, registry, or persisted worker state. Ordinary
resources, queue items, repository calls, and Driver observations never repeat
`installationId`; exported audit events retain it.

Before each infrastructure call, reload current persisted IAM policy and the
initiating actor, resolve the exact Namespace, recheck the live claim, and
authorize the operation using the current policy. Provisioning rechecks the
existing collection-scoped Namespace `create` grant that admitted the resource,
while resolving the exact persisted Namespace and enforcing current restrictions
against that Namespace. A still-valid collection-only grant must remain
sufficient; do not silently require an exact-Namespace `create` grant or a new
`operate` permission. Deletion rechecks `delete` on the exact Namespace.
Missing or revoked identity, denied permission, incompatible target, wrong
Namespace, or invalid Driver observation never invokes Compute. Transient IAM
or Driver unavailability retries with existing bounded backoff; an actual
authorization denial is a permanent, attributable failure.

Dispatch target `ready` only while the Namespace remains `provisioning`, through
`ComputeDriver.ensureNamespace`. Dispatch target `deleted` only while it remains
`deleting`, through `ComputeDriver.deleteNamespace`. A stale superseded target
completes without an infrastructure effect. Driver calls occur outside database
transactions and retain the exact Namespace identity.

### Idempotent effects and fenced finalization

The existing semantic key identifies the operation across duplicate requests,
worker restarts, and attempts. Immutable Namespace identity plus persisted
target and current lifecycle status distinguishes provisioning from teardown;
no generation, second identifier, or additional deduplication table is needed.

Heartbeat the current claim during each Driver call. `ensureNamespace` must
observe or reconcile the same backing namespace and one Namespace-owned gateway;
`deleteNamespace` must treat already verified removal as success. Retry
ambiguous effects only when the exact infrastructure can be observed or the
operation can be repeated idempotently. A lease fences PostgreSQL state, not an
external effect that has already started.

After the call, use a minimal
`PostgresPlatformState.transactWithQueue((unit, transactionQueue) => ...)` seam
that binds the state unit and `PostgresWorkQueue` to the same existing
transaction client. Within that short transaction, call
`transactionQueue.heartbeat(claim)` first: its existing atomic update verifies
the semantic key, claim token, `claimed` state, and unexpired lease while locking
the work row. If it returns no claim, abort before any Namespace mutation or
audit. Otherwise lock and recheck the exact Namespace, persist its OCC-owned
observation and lifecycle audit, and invoke the existing transaction-bound
`complete`, `retry`, or `fail` before committing. A lost fence or queue/audit
error rolls back every resource and audit change. Add no fencing API, schema,
or lock held across a Driver call.

Complete provisioning only when `namespaceReady` and `gatewayReady` are both
true; then OCC sets `ready`. Incomplete or retryable observations preserve
`provisioning` and retry. Permanent provisioning failure sets `failed` and
terminalizes its work. Deletion succeeds only when both `namespaceDeleted` and
`gatewayDeleted` are true; then OCC writes its durable tombstone and completes
the work. Incomplete deletion remains `deleting` and retries; a permanent
deletion failure preserves `deleting` and records a terminal failure.

## Implementation

1. Extend [PostgresWorkQueue](../../../../packages/occ/src/state/postgres-work-queue.ts)
   only where needed to apply `revision_id IS NULL` consistently to claim, both
   stale/exhausted recovery sweeps, and pending/health counts; reuse its existing
   claim, lease, heartbeat, retry, recovery, and fenced completion methods.
2. Refactor [OCC lifecycle handling](../../../../packages/occ/src/index.ts) and its
   [PostgreSQL state adapter](../../../../packages/occ/src/state/postgres-state.ts)
   with the minimal same-client `transactWithQueue(unit, transactionQueue)` seam
   so policy refresh, collection-aware exact-Namespace authorization, Driver
   dispatch, OCC observation, lifecycle audit, and existing heartbeat-fenced
   queue finalization share the prescribed contract; remove metadata-only Agent
   enqueueing.
3. Add a dedicated polling worker entrypoint under
   [apps/controller/src](../../../../apps/controller/src), compose the existing
   development IAM and Compute Drivers, and report health through structured
   process events. Invoke the worker directly with Node; do not change a
   dependency manifest or add another HTTP listener.
4. Extend [controller lifecycle tests](../../../../tests/integration/controller-lifecycle.test.mjs),
   [PostgreSQL restart tests](../../../../tests/integration/postgres-restart-recovery.test.mjs),
   and [durable platform integration tests](../../../../tests/integration/postgres-platform-state.test.mjs)
   with two-Namespace end-to-end execution, restart recovery, denial, stale
   fencing, duplicate-effect prevention, deletion proof, and revision exclusion
   from claim, both recovery sweeps, and supported backlog counts.

## Verification

| Required outcome      | How to verify                                                                                                                              |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Independent worker    | Use an isolated disposable PostgreSQL database and separate real API/worker processes; bootstrap once and reject pre-initialization work.  |
| Namespace readiness   | Create two Namespaces; poll until each becomes ready only after its exact backing namespace and one gateway report ready.                  |
| Authorized deletion   | Delete an empty Namespace; verify exact teardown, durable tombstone, and unaffected sibling Namespace.                                     |
| Atomic admission      | Inject mutation, audit, or enqueue failures; verify no partial resource/work commit and no denied side effect.                             |
| Current authorization | Preserve valid collection-only Namespace `create`; revoke the actor, grant, or exact-Namespace restriction and verify attributable denial. |
| Safe retries          | Interrupt a worker during a Driver call; recover its lease, observe one logical infrastructure effect, and reject the old claim token.     |
| Atomic finalization   | Expire a claim before finalization or inject an audit/queue failure; verify Namespace status, audit, and completion roll back together.    |
| Work boundaries       | Create Agents without work; exclude revision rows from claims, both recovery sweeps, and supported pending/health counts.                  |
| Concurrency and scope | Preserve one claimed operation per Namespace/Agent, independent Agent lanes, exact Namespace ownership, and implicit Installation scope.   |
| Workspace quality     | Run focused integration tests, then `pnpm test`, `pnpm typecheck`, `pnpm build`, `pnpm openapi:check`, and `pnpm check:workspace`.         |
