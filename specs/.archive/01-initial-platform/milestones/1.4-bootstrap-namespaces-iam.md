# Feature Spec: Milestone 1.4 — Bootstrap, Namespaces, and IAM

## Problem and Decision

Milestone 1.4 completes single-use bootstrap, native IAM, and isolated Namespace
lifecycle on the durable state introduced by
[`1.3-postgresql-persistence.md`](1.3-postgresql-persistence.md). One
administrator can create two Namespaces, and authorization, lookup, readiness,
deletion, identity, and gateway state cannot cross between them.

Each persisted platform has exactly one Installation with a stable ID. That ID
crosses configuration, admission, exported-audit, and deployment trust
boundaries, but ordinary Namespace and Agent resources, internal IAM policy,
repository operations, controller work, and Compute observations inherit the
singleton Installation implicitly. `namespaceId` remains the exact tenant
boundary.

The [authoritative design](../../../../docs/design.md)
governs architecture. The milestone plan
is noncanonical and conflicts with it on gateway ownership and cardinality.
M1.4 follows the authoritative design: exactly one Namespace-owned gateway is
realized through the Installation-selected `ComputeDriver`.

M1.4 reuses the M1.3 PostgreSQL schema, unit of work, audit repository, and
controller-work queue. It adds Groups, Restrictions, complete native IAM
evaluation, Namespace deletion state, and a deterministic fake gateway
lifecycle. It does not add another setup record, policy-version store, work
queue, controller identity, production Kubernetes adapter, or OAG admission
mode. The supporting alternatives and primary-source research remain in the
external architecture report.

### Source checklist

The implementation and proof must address the source checklist verbatim:

> - [ ] Implement audited, single-use Installation bootstrap and create the first
>       explicitly provisioned administrator.
> - [ ] Add a native `IAMDriver` that evaluates exact action, resource, Namespace,
>       role, binding, and applicable Restriction.
> - [ ] Implement Namespace creation, readiness, deletion, and scoped resource
>       lookup.
> - [ ] Create Namespace-local gateways through the selected `GatewayDriver`
>       without fixing the number of gateways assigned to a Namespace.
> - [ ] Mark a Namespace ready only when its required gateway capacity is ready;
>       reject Agent deployment when its assigned gateway is unavailable.
> - [ ] Ensure gateway ownership remains with the Namespace, independent of any
>       Agent or revision, whether the Namespace has one gateway or several.
> - [ ] Verify two Namespaces can coexist without resource discovery, mutation,
>       routing, or identity crossing between them.
> - [ ] Reject bootstrap reuse, unknown identities, missing grants, unavailable
>       authorization, and unauthorized Namespace operations.

For the fourth through sixth items, `ComputeDriver` owns one logical gateway per
Namespace. The M1.4 fake proves the contract; production
`KubernetesComputeDriver`, continuous dispatch, and upstream routing remain
follow-on work.

## Scope

### Changes

- Complete M1.3 bootstrap so the committed Installation, first Principal,
  administrator Role with embedded Permissions, AccessBinding, and success
  audit are the single durable setup result.
- Extend M1.3 IAM persistence with Groups, direct Group membership, and
  deny-only Restrictions; complete `OCCIAMDriver` evaluation and hydration.
- Add exact Namespace deletion, terminal tombstones, readiness transitions, and
  the Namespace gateway methods on `ComputeDriver`.
- Prove gateway lifecycle with a deterministic one-shot fake and gate the
  existing deploy placeholder on persisted Namespace readiness.
- Remove repeated Installation IDs from singleton-scoped internal and ordinary
  API contracts while retaining them at explicit trust and export boundaries.
- Extend conformance coverage across two Namespaces.

### Does not change

- M1.3 queue claims, leases, retry policy, idempotency, audit storage, or
  transaction boundaries.
- Production Driver dispatch, reauthorization, watches, readiness decay, or a
  Kubernetes client; M1.5 and follow-on production work own them.
- OAG, production ingress, public IAM CRUD, Agent revisions/workloads, routing,
  secrets, or workload identity behavior.
- Multiple logical gateways, nested Groups, executable policy expressions,
  Cedar/OPA/OpenFGA, CRDs, or non-Kubernetes production compute.

## Contract

### Singleton Installation boundary

Each state store owns exactly one persisted Installation. Its stable `id`
remains visible through `GET /installation` and is retained by server
configuration, admission and trust validation, exported audit events, and
external deployment boundaries. No request can select a second Installation.

Ordinary Namespace and Agent API resources do not repeat `installationId`.
Internal IAM identities and policy records, `ResourceRef` values, Compute
lifecycle observations, repository arguments, and controller-work objects also
inherit their Installation from the selected singleton store. They carry
`namespaceId` whenever exact tenant ownership is relevant; child resources and
work cannot cross Namespace boundaries. Storage keeps the singleton
Installation row and does not add redundant Installation columns to child
tables.

### Bootstrap and native IAM

The absence of the singleton `occ.installation` row is the only uninitialized
state; M1.4 adds no setup row or concurrent-bootstrap protocol. Development
bootstrap uses the explicit server-configured setup identity from M1.3. The
request supplies only the Installation name.

One transaction inserts the Installation, first Principal, built-in
administrator Role with its complete M1.4 Permissions, Installation-scoped
AccessBinding, and success audit. A unique singleton constraint permits one
commit. Failure rolls back the entire result. Initialized startup disables the
route, hydrates persisted IAM, and rejects reuse as `409 INSTALLATION_EXISTS`.
Normal APIs remain unavailable until bootstrap commits.

M1.4 preserves the M1.3 one-database/one-Installation model: IAM tables do not
repeat `installation_id`; nullable `namespace_id` distinguishes singleton-wide
and Namespace scope. Internal IAM identities and policy records likewise omit
the implied Installation ID. It adds:

- Groups containing direct Principals only, with membership in the same scope;
- AccessBindings whose subject is exactly one identity or Group; and
- deny-only Restrictions matching action, resource kind, optional exact
  resource ID, and optional Namespace.

Database constraints reject cross-Namespace membership, Roles, bindings, and
Restrictions. Public policy-management routes remain deferred; bootstrap and
internal test fixtures are the only M1.4 policy-authoring paths, so application
update/delete grants are not broadened.

Initialized startup hydrates `OCCIAMDriver` from one transaction-consistent
persisted view. It denies an unknown or wrong-scope identity, expands direct
Group membership, requires an exact binding and Role Permission, and then
applies every matching Restriction; any Restriction denies. Invalid, ambiguous,
unsupported, or unavailable IAM denies without a fallback Driver.

M1.4 preserves the M1.2 authorization contract: the fully qualified route action
is audit evidence, while IAM evaluates the existing exact
`PermissionAction + ResourceKind + ResourceRef` tuple without duplicating the
singleton Installation ID. `ResourceRef` retains its exact resource ID and, for
tenant resources, its `namespaceId`. Create targets the exact container defined
by the route registry. Lists authorize `read` per candidate: denial filters
that candidate, while IAM unavailability or an invalid decision fails the
entire list.

### Namespace lifecycle and readiness

Namespace creation reuses the M1.3 mutation transaction: insert
`status = provisioning`, append success audit, and enqueue the existing exact
Namespace `reconcile` work. The work identity derives from Namespace ID and the
target status; M1.4 adds no second lifecycle-intent table or generation field.

The M1.4 conformance harness claims that work and invokes a deterministic fake
of the selected `ComputeDriver` Namespace lifecycle. The fake ensures or deletes
the exact backing Namespace and exactly one Namespace-owned gateway. It returns
only bounded readiness or failure; it cannot choose placement, identity,
cardinality, or another Namespace. This is test execution, not the production
controller loop or Kubernetes implementation.

OCC is the only writer of public Namespace status. A successful observation for
a row still in `provisioning` changes it to `ready`; a permanent failure changes
it to `failed`; a retryable or incomplete result leaves it `provisioning`.
`ready` means both the backing Namespace and its one gateway are ready. M1.5 may
add continuous observation and readiness decay without changing that predicate.

`DELETE /namespaces/:namespaceId` authorizes the exact Namespace, locks it, and
accepts only a Namespace with no Agents. The transaction changes status to
`deleting`, appends audit, and enqueues exact Namespace reconcile work, returning
`202`. New children and deployments are then rejected. After the fake confirms
gateway and backing-Namespace removal, OCC sets `deleted_at`; list and exact read
treat the tombstone as absent. The row remains to satisfy M1.3 retained work,
audit, and `RESTRICT` ownership. Name reuse and physical retention remain
follow-on policy.

Every repository operation derives the singleton Installation from its selected
store and validates the exact Namespace and child-resource owner. Wrong-owner
lookup returns nondisclosing `404`; a correctly scoped IAM denial returns `403`.

### Deployment gate, API scope, and audit

The existing deploy route resolves and authorizes the exact Agent. If its
Namespace is not `ready`, it returns `409 NAMESPACE_NOT_READY` and creates no
revision or work. A ready Namespace reaches the existing unimplemented boundary
and returns `409 DEPLOYMENT_NOT_IMPLEMENTED`; M1.6 owns deployment.

M1.4 keeps the M1.2 route model: bootstrap and Namespace administration are
Installation-scoped, while Namespace-owned children use nested paths and exact
IAM targets. `GET /installation` returns the stable Installation `id`; ordinary
Namespace and Agent responses omit `installationId`. Namespace IDs come from
paths and persisted ownership, never body, query, or scope-override headers.
Production exact-Namespace admission remains an OAG concern; M1.4 adds no
`admissionScope` registry.

Exported audit events retain the Installation ID and record actor, action,
exact resource, Namespace scope, selected `IAMDriver`, applicable Restrictions
and outcome, and result. Bootstrap, IAM denial, Namespace transition, fake
lifecycle result, deployment rejection, and deletion are attributable.
Credentials, foreign-tenant identifiers, and raw Driver payloads are excluded.
Authorization failure occurs before mutation or fake Driver invocation.

## Implementation

1. Extend `packages/contracts/src/` with Groups, Restrictions, tombstoned
   Namespace responses, stable deletion errors, and Namespace lifecycle methods
   on `ComputeDriver`; remove the separately selectable `GatewayDriver` and
   repeated Installation IDs from ordinary resources, IAM, `ResourceRef`, and
   Compute lifecycle observations.
2. Extend the M1.3 Drizzle schema, migrations, repositories, hydration, and
   conformance port with Group membership, Restrictions, same-scope constraints,
   `deleted_at`, status updates, exact logical deletion, and singleton-derived
   repository and controller-work ownership.
3. Complete `packages/iam/src/index.ts` with direct-Group expansion,
   deny-overrides evaluation, and fail-closed persisted hydration.
4. Add OCC bootstrap completion, Namespace delete/readiness use cases, fake
   lifecycle handling, deployment gating, and audit; wire the route changes in
   `apps/controller/src/` without a production worker or Kubernetes dependency.

## Verification

| Outcome              | Required proof                                                                                                                             |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Single-use bootstrap | one complete transaction succeeds; failure is empty; initialized restart hydrates IAM; reuse is rejected                                   |
| Singleton scope      | stable Installation ID stays at trust/export boundaries; ordinary resources, IAM, work, and Compute observations omit it                   |
| Native IAM           | direct and Group grants work; wrong action/resource/scope, missing grant, matching Restriction, invalid state, and unavailable IAM deny    |
| Scope integrity      | database and repository tests reject every cross-Namespace membership, binding, Restriction, and lookup                                    |
| Namespace lifecycle  | create atomically records `provisioning` plus audit/work; repeated fake handling is idempotent; only complete readiness becomes `ready`    |
| Deletion             | unauthorized or nonempty deletion fails; authorized empty deletion becomes hidden only after fake teardown and remains a durable tombstone |
| Deployment gate      | an unready Namespace returns `NAMESPACE_NOT_READY` with no revision, work, or Driver call                                                  |
| Isolation            | Namespace A cannot discover, mutate, route to, bind identity to, or receive identifiers from Namespace B                                   |
| Quality gates        | `pnpm test`, `pnpm openapi:check`, `pnpm typecheck`, `pnpm build`, and `pnpm check:workspace` pass                                         |

Run `pnpm format:check` for its declared active-workspace globs. It excludes
`specs/**`, so check this document with
`pnpm exec prettier --check specs/01-initial-platform/milestones/1.4-bootstrap-namespaces-iam.md`.

Exit evidence bootstraps one administrator, creates two isolated Namespaces,
drives both through the deterministic gateway fake, proves exact authorized
visibility, and exercises denial, unavailability, deployment gating, and logical
deletion. It does not claim production Kubernetes or controller convergence.
